# 決策紀錄(Decision Log)

本檔案記錄專案中「**評估過後決定不做**」或「**選了 A 而不選 B**」的決策,以及背後的理由。留在這裡的目的是讓後續接手的人不必重新推理一次,也不會誤以為「當初沒想到」。

每項決策的格式:背景 → 決定 → 理由 → 什麼情況下會翻轉。

---

## D1:不導入資料庫(DB),以 JSON 檔案為持久層

> **已過時**:D6 移除整個持久層後,本決策的「JSON 檔」部分不再適用(系統已無 `repository/` 與 `data/`)。但「不導入 DB」的結論仍然成立,理由改由 D6 承接。以下保留原文以記錄當時的推理。

### 背景

購物車、促銷折扣、優惠券都是電商常見的資料。一般直覺是「購物車要存 DB」「優惠券要留發行紀錄」,尤其促銷有季節性(如 11.11)、會隨年度迭代,優惠券也該記錄由哪間公司發行。這些特性聽起來都指向 DB。

### 決定

**MVP 不使用 DB**,持久層統一由 `repository/json_store.py` 以 JSON 檔案處理(`data/seed.json`、`data/runtime.json`)。

### 理由

核心判斷:**DB 的價值在「操作的種類」,不在「資料的性質」。** 資料具有季節性、需迭代、需留紀錄,描述的是資料在生產環境的特徵;但 DB 值不值得,取決於系統是否需要對它做查詢、版本回溯、審計、並發寫入。

本題的驗收方式給了明確線索:`tests/fixtures/case_a.txt` 裡,`2015.11.11|0.7|電子` 與 `2016.3.2 1000 200` 是**隨結算請求一起傳進來的輸入參數**,不是被系統查詢的常駐實體。系統從不問「2015 年當時生效的是哪幾檔促銷」,所以版本回溯能力在 MVP 裡是死碼。

其餘理由:

1. **題目範圍**:依賴白名單只有 fastapi、uvicorn、pytest、httpx;題目明說「不要加入本次範圍以外的功能」「不要過度設計」。雖然 stdlib 的 `sqlite3` 不受白名單限制,但為幾個欄位付出 schema 定義、連線管理、測試隔離的成本,屬於教科書級的過度設計。
2. **資料流向設計**:題目把促銷與優惠券當成**每次結算的輸入**,而非預存常駐資料;`seed.json` 已足以承載。
3. **測試成本**:「需要儲存或日期的類別,在建構時從外部傳入」是題目指定的測試模式。JSON / 記憶體 store 讓單元測試不必建表、清資料;換 DB 會吃掉「自動化單元測試」這個評分項的投資。
4. **OOP 分數不在這裡**:ORM 路線最容易長出貧血領域模型(物件只是欄位容器,邏輯跑到 service 或 SQL)。題目要的 OOP 在 `domain/`——`Cart` 持有 `CartItem`、`Promotion` 與 `Coupon` 是有行為的物件。

### 什麼情況下會翻轉(滿足任一項即導入 DB)

- 後台需要對促銷 / 優惠券做 CRUD(而非只改 seed 檔)
- 需要回溯「某日期當時生效的是哪幾檔促銷」
- 需要多個管理員並發寫入同一份資料
- 審計軌跡(誰、何時、改了什麼)成為明確需求
- 出現跨資料表查詢或報表需求

### 翻轉成本

接近零。`repository/` 是唯一讀寫檔案的地方,`domain` 與 `services` 不碰檔案。將來把 `json_store.py` 換成 `db_store.py`,領域層與服務層一行都不用改。

## D2:資料職責分類——事實 / 規則 / 衍生值

### 背景

若要區分「什麼該暫存、什麼不該」,需要一套判斷依據,否則容易把所有資料混在同一層。

### 決定

系統內的資料依職責分為三類,**衍生值絕不暫存**。

| 類別 | 定義 | 範例 | 處理方式 |
| --- | --- | --- | --- |
| **事實** | 使用者或系統的選擇,本身不會推導出別的 | 購物車裡有 ipad × 2、session 識別 | 可以暫存 |
| **規則** | 折扣與判斷條件,是計算的**輸入** | 電子品類 0.7 折、優惠券門檻 1000 折 200 | 走定義好的來源(seed / runtime),**不暫存** |
| **衍生值** | 從事實 + 規則算出的數字 | 小計、折扣金額、合計 | **每次現場重算,不落地** |

### 理由

同一份事實配上不同日期或促銷,結果就不同。把 3083.60 存起來,一旦「當前日期」被後台覆寫,暫存的數字立刻是錯的,還得額外做失效判斷。題目要求「日期由參數傳入、業務規則寫成純函式」,正是確保**每次結算從輸入重算**,這與暫存計算結果直接衝突。

對應到分層:

```
暫存層      → 只放事實(購物車品項、session 識別)
設定來源    → 放規則(seed / runtime.json:目錄、促銷、優惠券、日期覆寫)
計算層      → 衍生值,每次從上兩層現場算,不落地
```

把促銷與優惠券跟購物車一起塞暫存,等於把「世界長怎樣」和「使用者做了什麼」混在同一層。

## D3:購物車錨點用 session,不做登入系統

### 背景

購物車要跨畫面共享、要綁定使用者,直覺上需要登入。但登入帶來密碼雜湊、token 管理、HTTPS 等一整套安全表面。

### 決定

**MVP 不做登入系統**。後端購物車以 session 為錨點:首次造訪由後端產生不可猜的 session id,寫入 `httpOnly` cookie,購物車 API 一律以該 cookie 識別。

### 理由

1. **題目範圍**:業務規則清單(促銷、優惠券、結算、日期覆寫)完全沒有登入、會員、歷史訂單。登入是獨立功能,做了是範圍蔓延,對「算出正確結算金額」這個核心評分項毫無幫助。
2. **完整性不等於做全集**:面試題的「完整」指把指定業務規則實作完並有測試覆蓋,不是把電商所有功能做一遍。
3. **安全**:session id 放 `httpOnly` cookie,前端 JS 讀不到,XSS 偷不走;比前端 localStorage 存 id 更安全。
4. **留好接點**:服務層以「一個錨點字串」當存取 key。現階段錨點 = session id;未來若加登入,錨點改 = user id,並做一次 session → user 的購物車合併即可。

### 什麼情況下會翻轉

- 出現會員專屬價格、歷史訂單查詢、跨裝置購物車同步等**需要使用者身份**的需求。

## D4:金額在後端是唯一信任來源

### 背景

前端已能算出合計(顯示用)。若結算時直接採用前端傳來的金額,會有嚴重安全漏洞。

### 決定

**結算時後端只收「商品名 + 數量」,價格由後端查 `CATALOG` 重取**,促銷與優惠券折扣也全部在後端計算。前端的金額僅供顯示。

### 理由

攻擊者用瀏覽器 devtools 改掉前端 `cart` 物件裡的單價,就能把 2399 改成 1 元結帳。這條規則**不受登入或儲存方案影響**,是底線。

對應實作約定:

- 後端金額一律 `Decimal`,四捨五入到小數 2 位
- 前端顯示用金額以整數「分」計算(`priceToCents` / `centsToText`),避免 float 小數誤差,精神與後端 `Decimal` 一致

## D5:查詢功能先做輸入框,不接後端

### 背景

商品瀏覽頁需要查詢框。可以立刻做查詢 API,也可以先做前端過濾。

### 決定

查詢框做出輸入與過濾效果,但**純前端過濾已載入的 18 項商品**,不發送請求。

### 理由

目前商品只有 18 項且全部已載入,後端查詢 API 沒有效能效益,做了屬範圍外的功能。等商品數量或查詢條件(如庫存、價格區間)真的需要伺服器篩選時,再將輸入框接上 API。

## D6:規格改為無狀態計算 API,價格與品類由請求帶入(反轉 D4)

### 背景

重讀題目後確認:題目給的產品目錄**只列品類與商品名,沒有任何單價**;單價只出現在案例輸入行(`1*ipad:2399.00`),格式明確是「數量*商品:單價」。目錄的真正角色是「商品 → 品類」的對照,讓品類促銷能套用;單價是**輸入的一部分**。

此外題目核心是「把案例資料餵進系統算出金額」,不是做一套完整的電商前台。

### 決定

系統縮為一支**無狀態計算 API** `POST /api/calculate`,並且:

1. **單價由請求 JSON 帶入**,不再由後端目錄重取——**D4 在此反轉**
2. **品類改為自由字串**,每個品項明確攜帶 `category`,不再有固定 `CATALOG` 與 `Category` 列舉
3. 促銷擴充為乘法 `rate` + 加法 `effect`,可限 `date` / `category`,省略代表全適用
4. 折價券欄位為 `minSpend` / `expiryDate` / `discount` / `effect`,**每次結算只能用一張**(題目原文,見 D7)
5. 移除商品 API、CLI 文字解析、網頁、`repository/`、`data/`

### 理由

1. **貼合題目**:目錄本無單價,價格只能是輸入。舊實作把案例的單價抄進 `CATALOG` 再拒絕不一致的輸入,等於只能原封重現 case_a / case_b,任何單價不同的案例都會被判成錯誤,違背「覆蓋各種一般與例外情況」。
2. **避免過度設計**:D4 的「後端為唯一價格來源」是電商安全考量(防前端改價),但本題無登入、無金流、無持久化,安全模型不存在,該防護是範圍外的複雜度。
3. **測試更直接**:案例即 JSON,`curl` 打 API 就是驗收,不需要文字解析器與 CLI 中介層。
4. **多張折價券**:題目規格明列「多張折價券疊加」為必要情境,故改為陣列依序套用;每次仍可只傳一張,不相衝突。

> **已修正**:本點對題目的解讀有誤。題目原文(request.md)是「每次結算只能用一張」,並無多張疊加情境;「多張疊加」來自使用者貼的 JSON 規格,非題目本身。實際採行單券規則,詳見 D7。

### 什麼情況下會翻轉

- 系統要接真實金流或會員價,出現「價格不可由請求帶」的安全需求 → 重新引入後端定價目錄,但品類對照與計算引擎可原樣保留
- 需要保存購物車或歷史訂單 → 重新引入持久層

### 翻轉成本

低。`domain/` 與 `services/` 是純函式,不碰檔案;價格來源只影響 `api/calculate.py` 的組裝方式。

## D7:折價券每次結算只能用一張(修正 D6 對題目的誤讀)

### 背景

題目原文([request.md](../request.md))明寫:

> 這些優惠券只要有效期內,都能夠用在任何一次購物中,但是**每次結算只能用一張**。

D6 實作時採用了使用者貼的 JSON 規格版本「coupons 收陣列、依序套用」,並在決策理由中記為「題目規格明列多張折價券疊加」。**該記述與題目原文不符**——多張疊加是 JSON 規格的擴充,不是題目要求。本決策修正回題目版。

### 決定

折價券**每次結算只生效一張**:API 仍收 `coupons` 陣列(相容不變),但只評估**陣列第一張**券,其餘忽略不計。`couponResults` 只回報該張券的結果。

### 理由

1. **貼合題目**:題目白紙黑字寫「每次結算只能用一張」,且原輸入格式(`2016.3.2 1000 200` 一行)本身就只有一張券的位置。
2. **API 形狀不變**:`coupons` 仍是陣列,單張情境(放一張)完全相容,既有呼叫端不需改。
3. **理由欄位保持兩種**:`reason` 維持 `expired` / `below_min_spend` 兩種,不為「被忽略的第二張」新增第三種理由,避免介面膨脹。

### 被忽略的後續券不回報

第一張以外的券既不生效也不出現在 `couponResults`。曾考慮過為它們回報 `reason: "only_one_allowed"` 之類的第三種理由,但題目沒有這個需求,且會讓「有效卻被略過」與「過期/未達門檻」兩種語意混在同一欄位,故不採。

### 什麼情況下會翻轉

- 規格明確要求「滿足條件的多張券都可折抵」或「自動選最優一張」→ 改回 `apply_coupons` 的逐張或擇優邏輯;`reason` 需相應擴充。

### 翻轉成本

低。只有 `services/calculator.py` 的 `apply_coupons` 與其單元測試需改;案例預期值(case-6、case-10)跟著調整。domain 模型與 API 層不用動。
